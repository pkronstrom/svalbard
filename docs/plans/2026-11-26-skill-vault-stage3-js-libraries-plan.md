# Skill vault stage 3: JS libraries, packing and HTML skills — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Four pinned JS library recipes with quickstarts, `svalbard-drive html pack` producing single-file HTML offline, seven HTML skills with tested templates, Natural Earth usable from the drive's query tools, and the two definition-of-done tests run and recorded.

**Architecture:** A `js-lib` recipe type maps to `lib/js/`; its `bundle:` entries extract trimmed npm packages into `node_modules/` trees, with pins generated by a `build-tools` command from an npm lockfile. `toolkit.Generate` writes each library's quickstart into `lib/js/<recipe>/docs/` (stage 1 indexes it). `html pack` embeds esbuild's Go API in `svalbard-drive`, resolves bare imports against installed trees, inlines everything it can and checks the result. HTML skills join `skills-core` with `requires:` on their library recipes.

**Tech Stack:** Go 1.26, `github.com/evanw/esbuild/pkg/api`, npm registry tarballs, Chromium and Firefox for development-time checks.

**Spec:** [2026-11-26-skill-vault-and-js-libraries-design.md](2026-11-26-skill-vault-and-js-libraries-design.md) (sections Definition of done, Recipe types and layout, Packing, Skill shape for small models, Catalog content, Staging 3).

**Depends on:** stages 1 and 2 merged.

## Global Constraints

- Every bundle source has a sha256 pin; pins come from the generator, never hand-edited.
- Trimmed extraction only: `package.json`, the browser builds a quickstart names, README, LICENSE (any case/extension), and `.d.ts`; self-contained UMD builds (Mermaid, Turf, `d3.min.js`) are a single file with no closure.
- Dependency trees are per recipe in npm lockfile layout; the same top-level package in two recipes is a catalog error. Node-only packages pulled by closures are not extracted.
- Portability per library is measured, one of `single-file`, `served`, `directory`; never set without a recorded run.
- `html pack` single-file output contains no `http(s)://` or protocol-relative resource reference, no relative `fetch`, and no missing local asset; warn above 10 MB.
- Browser targets: current Chromium and Firefox; Safari best effort; Web Serial/WebUSB marked Chromium-only.
- p5 is pinned to 1.11.x. Three.js quickstart uses `three/addons/...` imports.
- `maplibre-vendor` keeps its id, paths and every reference (`recipes/dep-defaults.yaml`, presets, saved `desired.items`, the map viewer) but is re-sourced from pinned npm tarballs; it and `js-maps` pin the same `maplibre-gl` and `pmtiles` versions, checked by a catalog test. Both stay on maplibre-gl 5.x: 6.x is ESM-only and breaks the viewer's classic-script load (catalog audit).
- Quickstart file names: a package name's `/` becomes `__` (`@jscad/modeling` → `docs/@jscad__modeling.md`) via `catalog.LibraryDocName(pkg string) string`, so stage 1's single-segment `lib/js/<recipe>/docs/<file>.md` rule indexes them.
- Skill requirements may use `type:<recipe type>` (stage 2).
- Keep Aven refs out of commits and committed docs.

## Review Focus

1. A page that imports a package present in two installed recipes at different versions (allowed only for nested deps) → pack resolves the importing recipe's own tree, never mixes versions in one bundle.
2. A page whose module script imports a library marked `served` (PMTiles) → single-file mode fails naming the library and suggesting `--dir`; `--dir` output opens through the drive's server.
3. A page that `fetch`es `./data.csv` → single-file mode fails with "relative fetch cannot work from file://; import the file instead" and the inlined-import path works.
4. An existing vault with `natural_earth_vector.gpkg.zip` at the vault root (today's broken install) → update moves it to `data/natural_earth_vector.gpkg`, unzipped, and removes the stray zip.
5. A pin generator run where the registry tarball's sha512 `integrity` doesn't match the downloaded bytes → the generator fails and writes nothing.

Each has a test in the task that owns the code (marked RF1–RF5).

## Owner direction, 2026-11-26: the smallest footprint that works

The packed HTML is small because the bundler keeps only what a page imports, so the stick needs one usable build of each library and nothing else. On exFAT with 128 KB clusters the cost is the number of files, not their bytes: `@jscad/modeling` is 1.6 MB in 1,100 files, which allocates about 140 MB.

- Per library the stick holds at most: the one browser build the quickstart imports (plus only the addon files a quickstart or skill names, for libraries such as Three.js), `package.json`, the licence, one quickstart, and one reference file.
- No alternative formats (UMD beside ESM, minified beside unminified), source maps, `src/` trees or test files. A self-contained single-file build is preferred wherever the project publishes one and it packs.
- Type definitions are not shipped as trees. Where a library needs them as reference, they are concatenated into the one reference file.
- Budgets are enforced by a catalog test: a maximum file count and allocated size (at 128 KB per file) per library and per recipe, with the measured numbers in the checkpoint. A recipe that exceeds its budget fails `make verify`.

**Decided: each JS library recipe is one archive on the stick, read in place.**
- `lib/js/<recipe>.zip` holds the recipe's `node_modules` tree (still trimmed to the one build per library, the addon files that are named, `package.json` and licences). Apply writes the archive; nothing is unpacked on the stick.
- `svalbard-drive html pack` resolves and loads modules from inside the archives through its esbuild resolve and load plugins. The portable-directory output and anything served live extract only the files they use, at that moment.
- Quickstarts and reference files stay loose under `lib/js/<recipe>/docs/`, because the document pass indexes files by vault path and the search contracts stay as they are.
- `maplibre-vendor` stays as loose files: the map viewer loads it directly in the browser.
- The budget test counts files on the stick (the archive, the docs) and the archive's size; the per-library content rules still apply to what goes into the archive.
- A user `js-lib` recipe gets the same treatment.

**Decided: the reference file is the project's own documentation at the pinned version**, its repository's Markdown docs joined into one file per library, licence checked per project and recorded in `libraries:`. Where a project has no Markdown docs (HTML or generated references, Three.js for example), the reference file is the README plus the concatenated type definitions, and the library is listed in the checkpoint as a documentation gap with a size for closing it.

Why, for the record: on exFAT with 128 KB clusters space goes by file count; measured on a real install, a tree of 19,532 small files with 553 MB of content takes 2.94 GB.

### Task 3: `js-lib` type and the pin generator

**Files:**
- Modify: `host-cli/internal/toolkit/toolkit.go` (`TypeDirs["js-lib"] = "lib/js"`), `host-cli/internal/catalog/catalog.go` (`Item.Libraries []Library`)
- Create: `host-cli/internal/catalog/libraries.go` (types, validation: top-level package unique across recipes)
- Create: `build-tools/cmd/js-lock/main.go`, `build-tools/cmd/js-lock/main_test.go`
- Test: `host-cli/internal/catalog/libraries_test.go`

**Interfaces:**
- Produces:
  - `type Library struct { Package, Version, License, Description, Entry, Portability, Quickstart string }` (`yaml` tags snake_case; `Entry` is an ESM specifier like `chart.js/auto` or a UMD global like `window.Papa`).
  - `ValidateLibraries(items []Item) error` — fails when one top-level `Package` appears in two recipes or a `Portability` is outside the three values; called from catalog load.
  - `js-lock -spec recipes/js/<id>.lock.json -out recipes/js/<id>.yaml`: reads a spec `{ "id", "packages": {"chart.js": "4.x"…}, "include": {"chart.js": [...]}, "umd": {"mermaid": "dist/mermaid.min.js"}, "tarballs": {"xlsx": {"url": "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz", "version": "0.20.3", "sha256": "<optional expected>"}} }`. `tarballs` entries bypass the registry: downloaded, hashed, checked against `sha256` when given, and their own dependencies resolved from the registry like any package. Version ranges must not cross a major the spec pins (`maplibre-gl: "5.x"`). It resolves with the registry's metadata (no npm binary), downloads each tarball, verifies its sha512 `integrity` (RF5), computes sha256, drops packages whose `package.json` has `"bin"` only and no `browser`/`module`/`exports` browser condition (Node-only), and writes the recipe's `bundle:` list in lockfile layout (`dest: node_modules/<name>` or `node_modules/<parent>/node_modules/<name>`). Hand-written fields (`libraries:`, `license:`, `description`) are preserved from the existing YAML.

**Files:**
- Create: `drive-runtime/internal/htmlpack/pack.go`, `drive-runtime/internal/htmlpack/check.go`
- Create: `drive-runtime/cmd/svalbard-drive/html.go`; modify `main.go` fast path (beside `skills`)

- Test: `drive-runtime/internal/htmlpack/pack_test.go` with fixtures in `testdata/` (a tiny fake `lib/js/x/node_modules` tree)

**Interfaces:**
- Produces:
  - `type Options struct { DriveRoot, Page, Out string; Dir bool }`
  - `type Result struct { Out string; Bytes int64; Portability string; Notices []string; Warnings []string }`
  - `Pack(ctx context.Context, opts Options) (Result, error)`
  - `Check(html []byte) []Problem` (`Problem{Kind, Detail string}`; kinds `remote-resource`, `relative-fetch`, `missing-asset`).
- Behaviour: collect `<script type="module">` blocks and `src`s, bundle each as IIFE. Bare imports resolve through an esbuild `OnResolve` plugin, not `NodePaths` (which is one flat list for every importer): from the page, a bare specifier resolves in the one installed recipe that provides it as a top-level package (catalog rule: there is exactly one); from a file inside `lib/js/<recipe>/node_modules/…`, it resolves by walking up that file's own `node_modules` chain within its recipe, as Node does (RF1); loaders `.css`→inline, `.csv`/`.txt`/`.geojson`/`.json`→text/json, `.wasm`→`binary`, fonts→dataurl; inline `<link rel=stylesheet>`; append a `<!-- licenses: … -->` comment from each bundled package's LICENSE first line; read portability from installed quickstart frontmatter: any bundled library `served`/`directory` → single-file fails (RF2). `--dir` writes `out/index.html` plus assets with relative paths.
- CLI: `svalbard-drive html pack <page.html> [-o out.html] [--dir]`; prints `wrote <out> (<size>, single-file)` or the problems, exit 1.
