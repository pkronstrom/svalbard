# Complete offline PlatformIO/ESP32 operation

Status: reviewed 2026-10-07; execution authorized by the user's Phase 5 continuation.

## Outcome and boundary

The existing `esp32-dev` pack must operate from a provisioned vault on a clean supported host without an installed Python or PlatformIO and without networking. Its default remains ESP-IDF. Bundled examples compile for ESP32, S2 and S3; upload and serial-monitor commands use the same bundled tools, with actual device operation verified only when hardware is available. The historical [embedded design](2026-04-02-embedded-dev-design.md) supplies the product direction; this repairs the current Go path rather than implementing its wider MCU wishlist.

No Arduino, other MCU packs, Windows, arbitrary external libraries/components, recipe version-update system, or new UI in this phase. A project requiring unprovisioned dependencies must report failure rather than claim offline readiness. Linux x86_64/arm64 and macOS x86_64/arm64 are provisioned targets; native execution acceptance is macOS arm64, with other hosts clearly recorded as unexecuted.

## Provisioned dependency closure

Use the existing standalone-Python builder and recipe dependency resolution. Pin PlatformIO Core 6.2.0 and espressif32 7.1.3 together with ESP-IDF 6.1, its compatible compilers, ULP tools, both GDB packages, ROM ELFs, CMake, Ninja, SCons, esptool and OpenOCD. S2/S3 also require the RISC-V toolchain for their ULP coprocessor even though their main CPU is Xtensa. Obtain archive URLs and checksums from the official registry, retaining the already corrected OpenOCD pin. Unsupported target acquisition must be an explicit error for this closure. Apply schedules an already installed standalone-Python builder when newly selected Python-package items need it; otherwise an existing `svalbard-python` ID would suppress installation of Core/IDF. Before generating a ready inventory, validate the requested PIO target coverage across realized archives and Python trees. Old incompatible versions, ambiguous legacy paths or missing target coverage must fail with concrete re-provision guidance; automatic installed-version upgrades remain Phase 7. Missing new dependencies use ordinary acquisition, not a general drift updater.

Bundle Core and IDF/esptool Python dependencies in separate existing `python-package` trees. Core and IDF have incompatible urllib3 constraints, so they must not share one Python package tree. Use the pinned PlatformIO builder's dependency dictionary, its transitive dependencies and Darwin chardet constraint as the authority for this PIO path; add any further dependencies demonstrated necessary by the actual example builds. Do not claim a standalone IDF CLI environment: the rolling official IDF 6.1 constraint file demands a kconfig version incompatible with PIO 7.1.3's ~=3.9.0 requirement. Declare dependencies explicitly, including the `svalbard-python` runtime, so individual recipes selected through customization retain their required closure.

Toolchain archives are acquired to `tools/platformio/packages/<platform>/` or directly to `tools/platformio/packages/` for shared archives. An internal `.svalbard/platformio.json` inventory uses `{"version":1,"packages":[...]}`. Each package has `path`, `sha256`, `owner`, `name`, `kind` (`tool` or `platform`) and `platform` (empty for shared or the normalized Svalbard target). It records realized archive identity, not a requested version. The required Python trees are `platformio-core` and `espidf-python` in the existing per-platform tools directory; the latter includes esptool dependencies as well as IDF dependencies. The host derives registry identity from canonical recipe URLs; actual local package version comes from the archive manifest. It never labels an older realized archive with a newly requested version. The existing single `sha256` cannot pin different per-host archives. Add only optional `platform_sha256` alongside `platforms`, keyed by the same target; old recipes remain valid and no vault manifest-version change is needed. Regeneration supports known older root-level realized paths; unknown/missing closure fails with a reprovisioning explanation.

A narrow official-registry mirror fallback must allow fresh acquisition when its preferred mirror fails. Read the registry's own mirror headers and bypass mechanism; preserve pinned checksums, caller cancellation and existing partial-download identity rules. Do not construct guessed artifact URLs or broaden fallback to unrelated downloads.

## Runtime preparation and cache ownership

The Go embedded action validates the current host's complete inventory, archive bytes and bundled Python trees before advertising readiness. It uses a small embedded Python bootstrap helper with the pinned Core package-manager APIs to install local archives, retaining owner metadata and proper extraction layout/symlinks. No host Python/Core fallback. Package post-install hooks are audited: the esptool pip hook is replaced by copying its already provisioned dependencies into `_contrib`; any unhandled hook fails clearly. Local package installation uses `skip_dependencies`, and networking/pip index access is disabled during preparation and use.

Build an ESP-IDF venv in the host cache using the bundled interpreter, copy the separate provisioned IDF dependency tree into its actual site-packages, and write the exact pinned builder's `pio-idf-venv.json` version/interpreter marker only after validation. The builder deletes PYTHONPATH, so inheriting that variable alone cannot provision IDF. Validate distributions/imports and esptool functionality before publishing readiness; do not bypass dependency checks with `.pio_skip_pypackages`.

Cache identity covers preparation-format version, host platform, absolute vault path, archive content hashes and bundled Python/package content identity. Relocation or changed content therefore selects a new generation. Default cache is scoped to this vault/host under the user's cache directory; retain the explicit `SVALBARD_PIO_CACHE` override as a cache root. A cancellable OS file lock serializes preparation. Install into a generation's final absolute path from the start: venv scripts contain absolute paths and cannot be renamed safely. A generation is usable only after an atomically written ready marker. Incomplete generations can be removed/retried; the previous successful generation is untouched. Cancellation terminates and reaps the bootstrap process group before cleanup/releasing the lock. Never garbage-collect a ready generation in this phase; lifetime leases and cache collection are deferred. Recheck readiness after acquiring the lock.

The shell reuses the temporary-rc mechanism in `internal/shell`, sourcing the user's rc then enforcing the bundled environment at the end; environment keys are merged without duplicates. The shell prepends bundled `bin/<platform>` so `pio`/`platformio` resolve to the stick. Set the selected cache as `PLATFORMIO_CORE_DIR`, disable telemetry/update checks and pip index use, and retain interactive host shell behavior. Remove the global `PLATFORMIO_BUILD_DIR`: each project's ordinary `.pio/build` owns its build output; an explicit user's override remains possible. The native action is the single implementation, with the historical shell script dispatching to it rather than maintaining a second extractor.

## User path

Provision the `esp32-dev` pack normally; no manual archive copying or warm host cache is required. Run the embedded development action through the vault menu or its alias. On first use it verifies and prepares the cache, then opens a shell with bundled commands. Copy the included blink project to a chosen host working directory, edit it, and run `pio run`. Subsequent use reuses a valid generation; cancellation during preparation is retryable. Moving the stick/mount path prepares a compatible new generation. Changed archive bytes invalidate cached preparation. Upload uses `pio run -t upload` and serial monitor uses `pio device monitor`; host USB permissions/drivers and connected hardware remain prerequisites.

## Acceptance

- Unit/integration fixtures cover shared/platform destinations, exact registry ownership, missing dependencies, flat/nested archives and symlinks through real Core extraction, changed-content refresh, relocation, independent project builds, lock contention and cancellation/retry without false readiness.
- Downloader fixtures cover failed mirror fallback and checksum disagreement while preserving Phase 2 partial-transfer tests.
- A normally provisioned macOS arm64 vault with a fresh isolated cache and no host Python/Core on PATH builds the actual included ESP-IDF examples with OS-enforced networking disabled. Verify ELF/bin artifacts, bundled esptool invocation, repeated use, relocation and a preparation cancellation/retry. Hardware upload/monitor operation remains explicitly unverified without a device.
- Registry closure/availability, catalog synchronization, all modules, affected races and all four runtime cross-builds pass. Do not mark Phase 5 complete if the real offline build fails.

## Evidence

The scratch Core 6.2.0 experiment successfully installs a local esptool archive with `PackageSpec(owner=..., name=..., uri=file://...)` and resolves the platform's registry owner/range. It also proves postinstall runs despite `skip_dependencies`, requiring the explicit offline esptool treatment. The preferred Contabo mirror refused the connection; official mirror iteration supplied the same pinned bytes from GitHub.
